1.2 Document y Node — las unidades de contenido

1.2 Document and Node — the units of content

  • Document: una unidad "grande" de contenido tal como la trae un loader. Por ejemplo, una página de un PDF, un archivo Markdown completo, una fila de una tabla. Tiene text y metadata (un dict libre).
  • Node (típicamente TextNode): la unidad "chica" lista para indexar. Es el resultado de chunkear un Document. Hereda metadata del documento padre, tiene su propio id_ y mantiene relaciones (prev, next, parent) para reconstruir contexto.
  • Document: a "coarse" unit of content as it arrives from a loader — a PDF page, a full Markdown file, a row of a table. It carries a text field and a free-form metadata dict.
  • Node (typically TextNode): the "fine" unit, ready for indexing. It's the result of chunking a Document. It inherits metadata from its parent, owns its id_, and tracks relationships (prev, next, parent) so you can reconstruct context later.

Los embeddings se calculan sobre nodos, no sobre documentos. Esa es la regla mental.

Embeddings are computed over nodes, not documents. Tattoo that on your mental model.

1.3 Loaders y Node Parsers

1.3 Loaders and Node Parsers

  • Loader / Reader (PDFReader, SimpleDirectoryReader, etc.): convierte una fuente externa (archivo, URL, base de datos) en una lista de Document.
  • Node Parser / Splitter (SentenceSplitter, TokenTextSplitter, SemanticSplitter): convierte Documents en Nodes. Es el "chunker". Cada uno tiene una estrategia distinta: por oraciones, por tokens fijos, por similitud semántica.
  • Loader / Reader (PDFReader, SimpleDirectoryReader, etc.): turns an external source — a file, a URL, a database — into a list of Documents.
  • Node Parser / Splitter (SentenceSplitter, TokenTextSplitter, SemanticSplitter): turns Documents into Nodes. It's the "chunker". Each one carries a different strategy: by sentence, by fixed token count, by semantic similarity.

1.4 Embeddings y Vector Stores

1.4 Embeddings and Vector Stores

  • BaseEmbedding: el modelo que convierte texto a vectores. Implementaciones: OpenAIEmbedding, HuggingFaceEmbedding, etc. Tiene dos métodos clave: get_text_embedding (para indexar) y get_query_embedding (para preguntas). Importante usar el mismo modelo en los dos lados.
  • VectorStore: la capa de persistencia de vectores. ChromaVectorStore, QdrantVectorStore, PineconeVectorStore, etc. Cada una envuelve el cliente nativo de su backend. La envoltura te da una API homogénea, pero te puede ocultar capacidades específicas del backend — esto va a ser importante después.
  • BaseEmbedding: the model that turns text into vectors. Implementations include OpenAIEmbedding, HuggingFaceEmbedding, and others. Two methods matter: get_text_embedding (for indexing) and get_query_embedding (for questions). Crucially, the same model has to power both sides.
  • VectorStore: the vector persistence layer — ChromaVectorStore, QdrantVectorStore, PineconeVectorStore, and so on. Each wraps its backend's native client. The wrapper gives you a uniform API, but it can hide backend-specific capabilities — and that detail will bite us later.

How does VectorStoreIndex behave with — and without — a vector DB?

El VectorStoreIndex tiene dos modos de operar según qué VectorStore le pases por debajo. Esto es una de las cosas que más confunde al principio porque LlamaIndex hace que parezcan iguales:

The mental shift to make: once a vector DB is in play, the index becomes a very thin layer. It barely computes anything — it just translates between LlamaIndex types (TextNode, NodeWithScore) and the backend's native types (raw Chroma dicts, etc.). That's why, in this codebase, VectorStoreIndex.from_vector_store(...) returns instantly: no data is loaded into memory, only a connection is opened.

Y por eso también es viable saltarse al backend nativo cuando una abstracción no alcanza, como hace ChromaFilterRetriever en este código (lo vas a ver en la sección 5).

And it's why dropping down to the native backend is a viable escape hatch when an abstraction falls short — exactly what ChromaFilterRetriever does here (you'll see it in section 5).

1.6 Retriever — quien hace la búsqueda

1.6 Retriever — the search worker

Un Retriever recibe una query (envuelta en un QueryBundle) y devuelve una lista de NodeWithScore. Su única responsabilidad es seleccionar nodos relevantes, no generar respuestas.

A Retriever takes a query (wrapped in a QueryBundle) and returns a list of NodeWithScore. Its single job is to pick relevant nodes, not to generate answers.

Cada Index sabe construir su propio retriever (index.as_retriever(...)), pero la interfaz BaseRetriever es pública y podés implementar la tuya — exactamente lo que hace el código que vamos a leer.

Every Index knows how to build its own retriever (index.as_retriever(...)), but the BaseRetriever interface is public — you can roll your own. Which is exactly what the code we're about to read does.

1.7 NodeWithScore y QueryBundle

1.7 NodeWithScore and QueryBundle

  • NodeWithScore: un Node + un score (float, "más alto = más relevante"). Es la moneda que circula entre retriever, postprocessors y response synthesizer.
  • QueryBundle: la representación rica de una query. No es solo un string: tiene query_str, opcionalmente un embedding pre-calculado, y metadata. Permite que distintos componentes pasen información extra sin cambiar la interfaz.
  • NodeWithScore: a Node plus a score (a float; "higher means more relevant"). It's the currency that flows between the retriever, postprocessors, and response synthesizer.
  • QueryBundle: the rich representation of a query. Not just a string — it carries query_str, optionally a precomputed embedding, and metadata. It lets different components attach extra information without breaking the interface.

1.8 Postprocessors

1.8 Postprocessors

Un BaseNodePostprocessor recibe la lista de NodeWithScore después del retrieve y devuelve otra lista (filtrada, reordenada, recortada). Acá viven los rerankers, los filtros por similitud mínima, los deduplicadores, etc. Son opcionales pero muy comunes en pipelines serios.

A BaseNodePostprocessor receives the post-retrieve list of NodeWithScore and returns another list — filtered, reordered, or trimmed. Rerankers, minimum-similarity filters, deduplicators all live here. Optional, but standard equipment in any serious pipeline.

1.9 Response Synthesizer y QueryEngine

1.9 Response Synthesizer and QueryEngine

  • Response Synthesizer: el componente que toma los nodos finales y los manda al LLM con un prompt para producir la respuesta. Tiene varias estrategias (compact, tree_summarize, refine) según cómo manejar contextos que no entran en una sola llamada.
  • QueryEngine: la composición de extremo a extremo. Junta retriever + postprocessors + response synthesizer y expone un método query(str) → Response. Es lo que devuelve index.as_query_engine().
  • Response Synthesizer: the component that takes the final nodes and ships them to the LLM with a prompt to produce the answer. It carries several strategies (compact, tree_summarize, refine) for handling contexts that don't fit in a single call.
  • QueryEngine: the end-to-end composition. It glues retriever + postprocessors + response synthesizer together and exposes a single query(str) → Response. It's what index.as_query_engine() hands you back.

Cuando armás algo a mano (como vamos a ver), subclaseás CustomQueryEngine e implementás custom_query(str) → str. Ahí decidís vos cómo se orquesta todo por dentro.

When you assemble it by hand (as we're about to see), you subclass CustomQueryEngine and implement custom_query(str) → str. That's where you take ownership of the orchestration.

¿En qué se diferencia LlamaIndex de LangChain?

How is LlamaIndex different from LangChain?

Las dos librerías tocan lo mismo (datos + LLMs) pero resuelven capas distintas:

Both libraries touch the same problem (data + LLMs) but solve different layers:

  • LlamaIndex es data-first: nace para resolver "tengo un corpus, ¿cómo lo indexo y lo recupero bien para inyectarlo en un prompt?". Es donde está más maduro: loaders, parsers, índices, retrievers, postprocessors, evaluación.
  • LangChain es orchestration-first: nace para componer cadenas de pasos (LCEL), agentes con herramientas, memoria conversacional, integraciones con APIs externas. El índice vectorial es solo un nodo más de la cadena.
  • LlamaIndex is data-first: it was born to answer "I have a corpus — how do I index it and retrieve from it well, so I can stuff it into a prompt?". That's where it shines: loaders, parsers, indices, retrievers, postprocessors, evaluation.
  • LangChain is orchestration-first: it was born to compose chains of steps (LCEL), agents with tools, conversational memory, integrations with external APIs. The vector index is just one more node in the chain.

No son competidores estrictos: en producción muchos los combinan (LlamaIndex para retrieve + LangChain para orquestar el agente que usa ese retrieve como tool). Este proyecto tiene una rama de cada uno justamente para comparar.

They're not strict competitors. In production, many teams combine them: LlamaIndex for retrieval, LangChain for orchestrating the agent that wires that retrieval as a tool. This project has a branch of each, precisely so you can compare them side by side.

¿Y por qué hacerlo así si el ChatEngine ya lo resuelve? Tres razones que aparecen al leer el resto del archivo:

So why do it this way if ChatEngine already solves it? Three reasons that surface as you read the rest of the file:

  1. Control del prompt. El sistema tiene tres capas anti-injection (separación estructural, nonce aleatorio para delimitar la pregunta, sanitización). Eso vive en build_prompt. Con ChatEngine heredás los templates del framework y para imponer este formato tendrías que sobreescribirlos — más código que el camino directo.
  2. El pipeline no encaja en los modos del ChatEngine. Acá el flujo es expand → retrieve × N → fuse RRF → rerank. condense_question reformula la pregunta y corre una retrieval; no soporta nativamente las múltiples queries + RRF. Para encajarlo igual habría que envolver toda la pipeline en un retriever custom solo para que ChatEngine la consuma — el envoltorio cuesta lo mismo que orquestarlo afuera.
  3. Paridad con la rama LangChain. El otro engine del proyecto también mantiene la memoria a nivel aplicación (vía RunnableWithMessageHistory, que es el equivalente LCEL: una capa de memoria alrededor de un chain stateless, no un objeto stateful como ChatEngine). Tener las dos ramas con la misma forma facilita la comparación lado a lado.
  1. Prompt control. The system layers three anti-injection defenses (structural separation, a random nonce to delimit the question, sanitization). All of that lives in build_prompt. With ChatEngine you inherit the framework's templates, and enforcing this format would mean overriding them — more code than just doing it yourself.
  2. The pipeline doesn't fit any ChatEngine mode. The flow here is expand → retrieve × N → fuse RRF → rerank. condense_question rewrites the question and runs one retrieval; it doesn't natively support multi-query + RRF. To make it fit, you'd have to wrap the whole pipeline in a custom retriever just so ChatEngine could consume it — and the wrapper costs as much as orchestrating it externally.
  3. Parity with the LangChain branch.   • arbitrary_types_allowed=True is required because LLM and InfinityRerank aren't pydantic-friendly types. Without it, pydantic complains at instantiation.
  • The mandatory method is custom_query(self, query_str: str) -> str. That's the contract CustomQueryEngine demands.

Cuatro cosas para subrayar:

Four things to underline:

  • El paso 1 invoca expand_queries(query_str), que pide al LLM (vía response_format=json_object) N_EXPANDED=2 paráfrasis. La query original se mantiene como queries[0]: si las paráfrasis se desvían del tema, el ranking original sigue pesando en la fusión.
  • El paso 2 corre una retrieval por cada query: con la expansión activada, son 3 retrievals (original + 2 paráfrasis), cada una con top_k=5. Eso da hasta 15 candidatos.
  • El paso 3 los funde con RRF (Reciprocal Rank Fusion) — ver el callout más abajo.
  • El reranker es un BaseNodePostprocessor — interfaz nativa. Recibe la lista y un QueryBundle, que es la representación que LlamaIndex usa para queries (encapsula el string + opcionalmente embedding + metadata). self.llm.chat(messages=...) devuelve un ChatResponse cuyo contenido vive en .message.content.
  • Step 1 invokes expand_queries(query_str), which asks the LLM (via response_format=json_object) for N_EXPANDED=2 paraphrases. The original query stays at queries[0]: if the paraphrases drift off-topic, the original ranking still carries weight in the fusion.
  • Step 2 runs one retrieval per query: with expansion enabled, that's 3 retrievals (original + 2 paraphrases), each with top_k=5 — up to 15 candidates total.
  • Step 3 fuses them with RRF (Reciprocal Rank Fusion) — see the callout below.
  • The reranker is a BaseNodePostprocessor — native interface. It receives the list plus a QueryBundle, LlamaIndex's representation of a query (string + optionally an embedding + metadata). self.llm.chat(messages=...) returns a ChatResponse whose content sits at .message.content.
¿Qué hace RRF? Toma N listas rankeadas (acá, las 3 listas que devolvieron las 3 retrievals) y combina sus posiciones en un único ranking fusionado. La fórmula es score(doc) = Σ 1 / (k + rank_i), sumada sobre cada lista donde el doc aparece. Constante k=60 (Cormack, Clarke & Büttcher 2009) — un valor alto suaviza la diferencia entre los primeros puestos, lo que evita que un único top-1 domine. En el código, rrf_fuse_nodes dedupea por node.get_content(): dos nodos con el mismo texto se colapsan a una entrada cuya score es la suma de sus contribuciones. El resultado se trunca a TOP_K_AFTER_FUSION=10 antes de mandarlo al reranker.
What does RRF do? It takes N ranked lists (here, the 3 lists from the 3 retrievals) and combines their positions into a single fused ranking. The formula is score(doc) = Σ 1 / (k + rank_i), summed across each list where the doc appears. Constant k=60 (Cormack, Clarke & Büttcher 2009) — a high value softens the gap between the top positions, preventing a single top-1 from dominating. In code, rrf_fuse_nodes dedupes by node.get_content(): two nodes with the same text collapse into one entry whose score is the sum of their contributions. The result is trimmed to TOP_K_AFTER_FUSION=10 before going to the reranker.
¿Qué hace un reranker? Después del retrieve + fuse tenés ~10 candidatos ordenados por similitud vectorial (rápida pero gruesa: compara embeddings pre-calculados). El reranker es un segundo modelo, esta vez un cross-encoder, que relee cada par (query, candidato) en conjunto y le pone un score de relevancia mucho más fino. Es más lento por candidato (corre el modelo entero por cada par) pero solo lo aplicás a los top-10, no a toda la base — por eso la pipeline tiene retrieve + rerank en vez de un único paso. Acá el reranker es un servicio HTTP (Infinity, sirviendo gte-multilingual-reranker-base) y se queda con los TOP_K_FINAL=3 mejores. Esos 3 son los únicos chunks que terminan en el prompt del LLM.
What does a reranker do? After retrieve + fuse, you have ~10 candidates ranked by vector similarity — fast but coarse, since it compares precomputed embeddings. A reranker is a second model, this time a cross-encoder, that rereads each (query, candidate) pair jointly and assigns a much finer relevance score. It's slower per candidate (the full model runs for every pair) but you only apply it to the top-10, not the whole corpus — that's why the pipeline is retrieve + rerank rather than a single step. Here the reranker is an HTTP service (Infinity, serving gte-multilingual-reranker-base) and it keeps the TOP_K_FINAL=3 best. Those 3 are the only chunks that make it into the LLM's prompt.
Memoria de corto plazo. El paso 5 también persiste el turno con append_turn(safe_question, answer). Esto guarda el par pregunta/respuesta en un ChatMemoryBuffer que vive en memoria del proceso (módulo memory.py), recortado a las últimas N entradas. La próxima vez que entre una query, recent_messages() trae esos turnos previos para inyectarlos en el prompt vía build_prompt(... history=...). Como dato sutil pero importante: append_turn se llama después del llm.chat, así que si la generación falla, no contaminás la ventana de memoria con un turno medio escrito.
Short-term memory. Step 5 also persists the turn via append_turn(safe_question, answer). That stores the question/answer pair in a ChatMemoryBuffer living in process memory (module memory.py), trimmed to the last N entries. On the next query, recent_messages() pulls those prior turns to inject them into the prompt via build_prompt(... history=...). Subtle but important detail: append_turn is called after llm.chat, so if generation fails you don't pollute the memory window with a half-written turn.

Worth highlighting:

  • Normalización de metadata. PDFReader devuelve page_label (string, 1-indexed). Se reescribe a {"source", "page"} (0-indexed) para que sea idéntico a lo que escribe la rama LangChain del proyecto — así los filtros funcionan igual en ambos engines.

7.3 query() — el override que arma todo

7.3 query() — the override that ties everything together

def query(self, msg: str) -> str:
    intent = detect_positional(msg)
    where, where_doc = None, None
    if intent is not None:
        manifest = load_manifest(self.engine_name)
        where, where_doc = build_filter(intent, manifest)

    engine = self._build_query_engine(where=where, where_document=where_doc)
    return engine.custom_query(msg)

Lo que hace de distinto vs. la implementación abstracta default:

What it does differently from the abstract default:

  1. Detecta intención posicional sobre el mensaje del usuario (lo explico abajo en detalle).
  2. Si hay intent, carga el manifest del engine y construye los filtros de Chroma (where, where_document).
  3. Construye el RagQueryEngine con esos filtros y delega custom_query(msg).
  1. It detects positional intent on the user's message (covered in detail below).
  2. If there's an intent, it loads the engine's manifest and builds the Chroma filters (where, where_document).
  3. It builds the RagQueryEngine with those filters and delegates to custom_query(msg).
¿Qué es la "intención posicional"? Es una heurística del MVP para detectar preguntas que apuntan a una posición dentro del libro y no a un tema. Por ejemplo: "resumime el capítulo 3", "¿qué pasa en la página 47?", "¿cómo termina el libro?", "¿cómo empieza?". Una búsqueda por similitud vectorial pura para estas preguntas devuelve cualquier chunk que mencione "capítulo" o "final" — ruido total. La función detect_positional(msg) usa regex para reconocer esos patrones (página N, capítulo N, al final, al principio) y, si matchea, devuelve un PositionalIntent = (kind, value) que el resto del flujo traduce a un filtro de Chroma antes del retrieval. La similitud vectorial sigue corriendo, pero acotada al subconjunto de chunks que cumplen el filtro.
What is "positional intent"? A heuristic in the MVP to catch questions that point at a position inside the book rather than at a topic. For example: "summarize chapter 3", "what happens on page 47?", "how does the book end?", "how does it start?". A pure vector-similarity search for those questions returns any chunk that mentions "chapter" or "end" — pure noise. detect_positional(msg) uses regex to recognize those patterns (page N, chapter N, at the end, at the beginning) and, on match, returns a PositionalIntent = (kind, value) that the rest of the flow translates into a Chroma filter before retrieval. Vector similarity still runs, but restricted to the subset of chunks that satisfy the filter.
¿Y qué es el "manifest"? Un JSON chiquito (backend/app/data/ingested_llamaindex.json) que mantiene un mapa {filename → cantidad_de_páginas} de cada PDF que se ingestó. Se actualiza cuando corrés el ingest. ¿Para qué se usa? Para los intents tipo "al final" o "al principio": necesitamos saber cuántas páginas tiene cada libro para construir un filtro tipo "páginas entre n_pages - 10% y n_pages - 1". Sin el manifest, no se podría calcular esa ventana. load_manifest(self.engine_name) usa engine_name ("llamaindex" o "langchain") para leer el archivo correcto — cada engine mantiene su propio manifest porque pueden tener corpus distintos.
And what is the "manifest"? A small JSON file (backend/app/data/ingested_llamaindex.json) that holds a {filename → page_count} map for every PDF that's been ingested. It's updated when you run ingest. What's it for? Intents like "at the end" or "at the beginning": we need to know each book's page count to build a filter like "pages between n_pages - 10% and n_pages - 1". Without the manifest, that window can't be computed. load_manifest(self.engine_name) uses engine_name ("llamaindex" or "langchain") to read the right file — each engine maintains its own manifest, since they may have different corpora.
Decisión gris #2. El engine se construye por request, no se cachea. Razón: los filtros dependen del mensaje del usuario y pueden cambiar de un request al siguiente. Y como las cosas pesadas (índice, LLM, embedder, cliente Chroma) ya son singletons cacheados, instanciar RagQueryEngine es básicamente construir una clase pydantic vacía — el costo es despreciable.
Gray decision #2. The engine is built per request, not cached. Reason: the filters depend on the user's message and can change from one request to the next. Since the heavy parts (index, LLM, embedder, Chroma client) are already module-level cached singletons, instantiating RagQueryEngine is essentially constructing an empty pydantic class — the cost is negligible.

@cached_property is used (rather than @lru_cache) because it's tied to the instance. This matters for tests: if a test patches get_index, a fresh service instance picks up the mock. With @lru_cache the cached value would be captured at module level and tests would contaminate each other.

Disclaimer importante. Diseñar código de producción pensando en cómo lo van a testear es generalmente mal criterio: el código de tests no debería filtrarse en decisiones de la API pública. La regla es al revés — los tests se adaptan al código, no el código a los tests. En un proyecto serio, esta justificación de elegir @cached_property sobre @lru_cache sería suficiente bandera amarilla como para revisarlo (¿podríamos haber hecho los tests más independientes? ¿no estamos dejando un acoplamiento implícito?). Acá nos lo permitimos porque es un MVP educativo y la diferencia entre los dos decoradores también tiene un argumento legítimo (el ciclo de vida del singleton es por servicio, no global), pero vale dejarlo dicho para que no internalices el patrón como buena práctica.
Important disclaimer. Designing production code around how it'll be tested is generally poor judgment: test code shouldn't bleed into public-API decisions. The rule runs the other way — tests adapt to the code, not the code to the tests. In a serious project, this justification for choosing @cached_property over @lru_cache would be enough of a yellow flag to revisit (could we have made the tests more independent? aren't we baking in implicit coupling?). We allow it here because it's an educational MVP and the difference between the two decorators also has a legitimate argument (the singleton's lifecycle is per-service, not global), but it's worth saying out loud so you don't internalize the pattern as best practice.
